# 外推算法验证 — 2026-10-28

**问题**：`--code-scan` 拟采用的解析外推算法（单点测 c → 对数换算直达目标码）能否按设想完成任务？

**结论**：**能**。真实两点互推双向前向命中同一目标码 0x11、核验 c=5.07（距 5.1 仅 −0.1 dB）；
误差预算合成总误差 ≈3.1 dB < 域单侧余量 11.9 dB（约 3.8 倍余量）。
前提：**外推后必须钉目标码实测验证一次**（允差 ±2 dB），这本来就是算法设计的一步。

## 被验证的算法

```
code_tgt = code_ref − round( 20·log10(c_ref / 5.1) / 1.55 )   # clamp [0x08, 0x18]
```
流程：钉安全中点 0x10 → 测 c_ref（30 s 中位数）→ 外推 code_tgt → 钉码实测验证；
不中（c_verify 出域或距 5.1 > ±2 dB）→ 用 c_verify 再外推一轮（至多 2 轮）→ 仍不中判数据异常拒写。

|---|---|---|---|

健康态单点 σ ≤ 0.32 dB → 随机码误差 ≤ 0.2 码；`--code-scan` 用 30 s 中位数更小。

### E 误差预算
| 项 | 值 |
|---|---|
| 随机（单点 σ 上界） | 0.3 dB |
| 系统（斜率 1.55 vs 开路 1.743，跨 12 码） | 2.3 dB |
| 测量（允许的空情档位差） | 2.0 dB |
| **合成（RSS）** | **≈3.1 dB** |
| 域单侧余量（5.1→1.3 / 5.1→20） | 各 11.9 dB |

总误差 < 单侧余量 ×(1/3.8)。方向性提示：判据斜率取保守值 1.55（< 1.743），
外推降码方向会**略过头**（偏低 ~2 dB @12 码），验证步实测后如偏低可上修一码——
这解释了"外推 + 验证"两步设计的必要性。

### 闭环仿真（模型内自洽检验）
4/4 轨迹参考点外推后落域。查证点为近码折算（归档轨迹无同链路多码点，
AGCON 段 `0x13` 恒定——AGC 不控制 IF 码，故轨迹不能提供斜率检验点），仅作自洽参考。

## 边界与注意

1. **归档轨迹的 AGCON 段不可用于斜率检验**：AGC 开时 `0x13` 不变、c 变化来自
   AGC 调其它增益级，c 不是 0x13 的单变量函数；`--code-scan` 全程钉 `0x0d=09`，
   与该场景不同。
2. conv_B 的 2.86 dB σ 说明**弱空情下 c 可漂**：外推窗内若空情档位突变，
   30 s 中位数也救不了——验证步 + 允差 ±2 dB 兜底；再不中走第二轮外推。
3. 算法不适用于 `c_ref` 本身出域到悬崖侧（削波失真）——参考码固定 0x10，
   远离 0x1c，规避此风险。

### 两条实机事实

1. **实测斜率存在空情依赖波动，1.55 是安全下界（两轮修正）**。
   首轮三机实测 1.62–2.09 dB/码（残差全负 −0.91/−1.21/−1.35），曾据此推断"按 1.55 换算会系统性过降约 1 dB"。
   **复验轮（R2）推翻该推断**：三机斜率 1.35–1.68 dB/码，残差变为 −1.31/+0.79/+0.31（两正一负，同目标码）。
   两轮合并：斜率 1.35–2.09、残差 −1.35…+0.79，符号不固定 ⇒ 残差是空情依赖的波动，不是固定系统偏差。
   处置不变且被强化：**外推斜率 1.55 + 钉目标码实测验证**的闭环是必要设计，允差 ±2 dB 覆盖观测到的全部波动。

2. **`.86` 的观测源必须用 tee，且恢复码要在关闭管道之前做**。
   `.86` 是 airband 机（无 readsb），内核 `dvb_usb_rtl28xxu` 会占用接口；
   守卫的裸 libusb 控制传输不 detach 内核驱动 ⇒ **只有在 `rtl_sdr` 管道运行（已 detach）时才能打开设备**。
   故 tee 模式下顺序必须是：钉原码（恢复）→ 再关管道。反序会导致恢复失败、设备停在实验码上。

### 执行中排除的两个假信号（勿重演）

- **同机并行双实例**：早期一次 `setsid nohup` 启动其实已成功（只是 SSH channel 等 EOF 超时），随后 systemd-run 又起一份 ⇒ 两份互钉码，读数离奇（c_verify 反而高于 c_ref）。判定：任何时刻**一台机只允许一个 verify 实例**，启动前 `pkill -f verify_node.py` 并核对 `pgrep`。
- **启动方式**：`nohup ... &` 会让子进程持有 SSH channel 的 fd，`exec_command` 等不到 EOF（表现为 `EXEC_TIMEOUT` 而进程其实已跑）。改用 `systemd-run --unit=fcverify --collect -p StandardOutput=file:...`，且 `file:` 为**追加**模式，重跑前必须 `rm` 日志。
